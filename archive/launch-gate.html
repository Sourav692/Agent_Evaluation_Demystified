The Launch Gate

The automated checkpoint that decides whether a build is allowed onto production traffic — and the single most consequential decision most agent teams under-engineer.

01 What it is

A launch gate (also called a release gate) is a binary, automated go / no-go check that a candidate build must pass before it is promoted from a pull request or staging environment into production. It sits at the end of the evaluation harness: the harness produces a report on a fixed, versioned test suite, and the gate turns that report into one decision — allowed: true or allowed: false — with a machine-readable list of reasons for a block.

It is deliberately narrow. A gate does not try to catch everything an agent could ever do wrong; that is the job of production monitoring, canaries, and rollback triggers running after launch. The gate's job is to catch what an offline suite can detect before any real user is exposed: known policy violations, quality regressions against a baseline, silent harm to a specific user segment, and cost blowups.

  • Offline, not live — it runs against a frozen golden set with frozen tool fixtures, so the same build always produces the same verdict. Determinism is what makes the gate trustworthy enough to block a release automatically.
  • Paired, not absolute — most checks compare the candidate build against a stored baseline report, not against a fixed target in isolation, so drift is measured relative to what is already in production.
  • Composite, not single-metric — a real gate runs several independent checks and blocks if any one fails. A single "accuracy went up" signal is exactly what lets dangerous regressions through, which is the whole reason the gate exists in the first place.

02 Why agentic systems need one specifically

In a single-turn LLM feature, a quality regression is usually visible in the aggregate metric. In an agentic system, three properties make aggregate metrics actively misleading:

  • Trajectories, not answers. An agent's output is a sequence of tool calls and decisions, not one response — so "quality" has to include whether it called the right tools, in the right order, and refused when it should have, not just whether the final text looks right.
  • Irreversible side effects. An agent with write access (filing a ticket, sending a payment, editing a record) can do real damage on a single bad trajectory. A policy violation here isn't a UX complaint — it's an incident.
  • Segment-hiding aggregates. A change can raise the overall success rate while quietly collapsing one tenant, one intent class, or one language — exactly the case worked through below.

03 A gate is not another metric

This is the part that's easy to miss: a launch gate isn't a fifth number added to a dashboard next to accuracy and latency. It's a decision layer sitting on top of whatever metrics you already compute. Your existing evals answer "how good is this build?" The gate answers a completely different question: "does this specific number, right now, mean the build is safe to expose to real users?" — and it answers that question the same way every time, without a person eyeballing a dashboard and using judgment.

Evaluation metrics what most teams build first
  • Measurement. A number: 84% accuracy, $0.21/run, 3.2s p95 latency.
  • Reported as an aggregate across the whole test set — one summary figure.
  • Descriptive. It tells you where you are. It doesn't tell you what to do about it.
  • A human reads it and decides, subjectively, whether "84%, down from 85% yesterday" is fine to ship.
  • Runs whenever someone remembers to — often ad hoc, in a notebook, before a demo.
  • Snapshot in isolation — no built-in comparison to what's already live.
Launch gate the policy built on top of those metrics
  • Decision. Consumes those same numbers and outputs one bit: allowed or blocked.
  • Broken into strata — checks the worst segment, not just the mean, so one metric can hide a collapsed tenant.
  • Prescriptive. A failing check has a hard consequence: the build does not get promoted. No judgment call required.
  • Automated and unattended — wired into CI/CD so it fires on every pull request, with no one needing to remember or interpret it.
  • Runs on every candidate build, against frozen, versioned fixtures, so the same build always gets the same verdict.
  • Paired against a baseline — the question is always "regressed vs. what's live," not "is this number good in a vacuum."

Put differently: your eval suite gives you signal. The gate gives that signal teeth. Most teams stop at the first half — they compute accuracy, cost, latency, maybe a groundedness score — and then a human glances at a dashboard before hitting deploy. That works until the day the aggregate looks fine and something underneath it isn't, which is precisely the segment-collapse case above: the metric existed, was correctly computed, and still let a 15-point regression through — because nothing was enforcing a rule on top of it.

Concretely, three things turn your metrics into a gate:

  • Thresholds with consequences, not just numbers. "Success rate: 84%" is a metric. "Block if success rate < 85%, or if any tenant drops > 3pt" is a gate — the same underlying computation, plus a rule that actually stops the merge.
  • Stratification. Compute every metric per-segment (per tenant, per intent class, per language), not only in aggregate, and gate on the worst stratum, not the mean.
  • Wiring, not reporting. The gate's output has to be read by something that can refuse to deploy — a CI check, a merge-block, a promotion pipeline — not just written to a dashboard someone might check.

04 The four checks

A launch gate built for an agentic system typically runs these four, in this order of severity:

01
Safety / trajectory assertions blocks absolutely

Hard rules encoded as "must not call X," "must confirm before Y," "must not skip approval." These never expire and are never traded off against a quality gain — a failure here blocks the release regardless of what every other check says.

02
Aggregate success floor threshold

Overall pass rate on the golden set must clear a minimum (e.g. ≥ 85%) and not regress against the baseline beyond a set tolerance. This is the metric everyone thinks of first — and the one that is least sufficient on its own.

03
Per-stratum floor threshold

No individual segment — a tenant, an intent class, a language — may drop by more than a set margin (e.g. 3 points), independent of what the aggregate does. This is what stops an aggregate improvement from shipping a segment collapse.

04
Cost ceiling threshold

Cost per successful run must stay under a set limit, and a build over it is blocked like any other failure. A quality gain that triples spend can still ship, but only as an explicit trade-off: someone raises the ceiling in a reviewed change to the gate config, so the higher spend is a decision on record rather than something that ships silently.

The suite these checks run against only works if it is stratified: built with a minimum case count per segment (so a small tenant isn't statistically invisible), and deliberately includes refusal, escalation, and adversarial cases — not just answerable questions — so an "improvement" that just answers more confidently doesn't look like progress.

05 Worked example — the segment collapse a gate is built to catch

A document Q&A agent serving eleven enterprise tenants

A retrieval change shifted weighting from lexical matching toward dense retrieval. Tested against the full golden set, it looked like a clean win.

The tenant's corpus leaned on heavy internal abbreviations — exactly what dense retrieval handles worse than exact lexical matching — but that tenant was only ~4% of the golden set, so its 15-point collapse was invisible inside a 2-point aggregate gain. It shipped, and the tenant escalated two weeks later.

What would have caught it: a per-stratum floor of "no tenant may drop more than 3 points regardless of the aggregate." That single check turns an invisible regression into an automatic block, before any customer sees it.

06 What the gate looks like in code

A minimal version is a pure function over a harness report — deterministic, versioned, and cheap enough to run on every pull request:

# The gate answers one question: may this commit be promoted?
# It runs four independent checks; a failure in any one blocks.

class ReleaseGate:
    STRATUM_FLOOR_DROP = 0.03   # no stratum may fall > 3 pts
    AGGREGATE_FLOOR    = 0.85
    COST_CEILING_USD   = 0.25

    def evaluate(self, build_id):
        report = self.harness.run(
            build_id=build_id,
            fixtures=frozen,             # deterministic suite
            paired_with=self.baseline,   # compare, don't judge in isolation
        )
        reasons = []

        # 1. safety — blocks absolutely
        if report.failed_safety_assertions:
            reasons.append("safety assertion failure")

        # 2. aggregate floor
        if report.success_rate < self.AGGREGATE_FLOOR:
            reasons.append("aggregate below floor")

        # 3. per-stratum floor — catches segment collapse
        for stratum, drop in report.stratum_deltas():
            if drop > self.STRATUM_FLOOR_DROP:
                reasons.append(f"{stratum} dropped {drop}")

        # 4. cost ceiling — blocks; raising it is a reviewed config change
        if report.cost_per_success > self.COST_CEILING_USD:
            reasons.append("cost per success over ceiling")

        return GateResult(allowed=not reasons, reasons=reasons)

07 What a gate is not

  • Not a substitute for production monitoring. A golden set of a few hundred cases has real statistical power limits — it reliably catches large regressions, not small ones. Small regressions are caught by live monitoring and an automatic rollback trigger, not the gate.
  • Not static. A suite built at launch describes launch traffic. Without a periodic drift check against production distribution, the gate quietly starts protecting a system nobody uses anymore.
  • Not a place for flaky tests. A safety assertion that fails intermittently gets deleted by an impatient team within a quarter — so fixtures must be frozen and deterministic, making determinism a safety property, not a convenience.
