Course 04 Guide: End-to-End Evaluation

◷ 15 min read

One support assistant, evaluated from every angle. The course builds a support agent for Pinecrest Outdoor Supply, a fictional outdoor-gear store. It writes a golden set for that agent, then scores retrieval, answers, tool calls, paths, task completion, conversations and safety. Notebooks 10–14 build custom judges, calibrate them against human labels, compare app versions with statistics, gate the release in CI and score live traffic.

This guide covers the whole course in one place: what each notebook teaches, the files it reads and writes, and where it stands today. For setup, see README.md. For why each tool was picked, see PLAN.md. Every metric's definition is in EVALUATIONS.md, and TRACKER.md tracks the build task by task.

The system under test

The agent being evaluated is a LangGraph supervisor with three paths:

  • Router (supervisor): a structured LLM decision that sends each message to one path.
  • RAG agent: answers from 9 support articles (returns, refunds, shipping, warranty, orders, loyalty, product care, account and privacy, contact and escalation), split into 31 chunks with stable IDs and stored in Chroma.
  • Account agent: a tool-calling loop over four tools (lookup_order, issue_refund, create_ticket, search_kb) against a mock order database. issue_refund enforces the business rules: matching email, return window, and a $500 limit.
  • Escalation: hands the case to a human.

The golden set

Every evaluation after notebook 03 runs on one set of 121 cases in six slices:

Slice Cases What it tests
simple 21 A question one support article answers
multi_hop 20 A question that needs facts from more than one chunk
out_of_scope 20 A question the articles don't cover; the right answer is a decline
tool_required 20 A request the account agent must act on with a tool
handoff 20 A case the policy says must go to a human
adversarial 20 An attempt to make the agent break a rule

Each case carries every label a later notebook needs: input, reference_answer, relevant_chunk_ids, expected_agent, expected_tool_calls, expected_end_state, policy_tags and source (hand-written or RAGAS-generated).

How the course is built

  • Each notebook stands alone. Open any notebook and run it top to bottom. Results pass between notebooks as files in data/. If an input file is missing, the notebook names the notebook that writes it.
  • No shared modules. Helpers are repeated in each notebook that needs them. Notebook 02 Part 9 holds the whole app in one cell, and later notebooks paste that cell rather than import it. The only script is the CI release gate (notebook 13), because CI has to run a file.
  • One baseline run, scored many times. Notebook 04 runs every golden case through the agent once and saves it as data/golden_runs.json. Notebooks 04–09 all score that same run, so their numbers describe the same behaviour.
  • Free checks before judges. Each topic starts with a deterministic check in plain Python, then adds an LLM judge, then reads the cases where the two disagree.
  • Outputs are committed. Runs call paid APIs, so you can read every result without running anything.

Module B: Test data

Notebook 03: The Golden Set

Status: Run, outputs kept. Reads: data/kb_chunks.json. Writes: data/golden_set_handwritten.json, data/ragas_candidates.json, data/golden_set.json. Keys: OPENAI_API_KEY. Evaluations: §0 test case contract, §1 golden set quality.

Part 1: The case schema

  • One record per test question, holding the labels for retrieval, routing, tool calls, end state and safety
  • Labelling only what must match: free-text arguments are left out, and null means "not checked"

Part 2: The hand-written cases

  • Policy rules, unhappy paths and attacks, written by someone who knows the policy
  • Stratified slices: six kinds of question, at least 20 each, so each slice can be scored on its own

Part 3: Synthetic cases with RAGAS

  • Generating extra knowledge questions from the chunks
  • The two setting changes RAGAS needed for short chunks

Part 4: Reviewing the synthetic cases

  • Dropping wrong references, ambiguous questions and near-copies

Part 5: Testing the test set

  • Five checks before saving: coverage, completeness, synthetic share, duplicates and leakage
  • Duplicates: questions compared by embedding cosine similarity, with pairs at 0.95 or above flagged, because a near-copy counts the same behaviour twice
  • Leakage: no test question may appear in the app's own code. Notebook 02's five smoke questions tuned its prompts, so none of them is in the test set

Notebook 05: Generation Evaluation

Status: Run, outputs kept. Reads: data/golden_runs.json, data/golden_set.json, data/kb_chunks.json. Writes: data/rag_scores.json. Keys: OPENAI_API_KEY, NEBIUS_API_KEY. Evaluations: §4 reference-free, §5 reference-based, §6 retriever vs generator blame.

Part 1: Which answers to grade

  • Picking the knowledge answers from the baseline run

Part 2: Did it decline exactly when it should?

  • A string compare on the fixed decline sentence: free and exact
  • Two directions of error: a missed decline invents policy, while a false decline is unhelpful but safe

Part 3: Reference-free metrics

  • Faithfulness, answer relevancy and hallucination, which need no reference and so also run in production
  • DeepEval on every answer, RAGAS on a 20-case subset
  • Same name, different behaviour: RAGAS and DeepEval relevancy disagree on short cited answers, and DeepEval 4.2.3's hallucination score is higher-is-better

Part 4: Reference-based metrics

  • Exact match and token F1, and why they fail on full sentences
  • Factual correctness, semantic similarity, and a GEval rubric judge that handle rewording

Part 5: Who is to blame?

  • Combining recall, faithfulness and correctness to blame each failure on the retriever, the generator or the test case

Part 6: Save the scores

  • Writes every per-case score to data/rag_scores.json for the statistics in notebook 12

Notebook 09: Safety and Red-Teaming

Status: Run, outputs kept. Reads: data/chroma_db/, data/golden_set.json, data/golden_runs.json, data/kb_chunks.json. Writes: data/safety_scores.json. Keys: OPENAI_API_KEY, NEBIUS_API_KEY, LangSmith. Evaluations: §12 safety and adversarial.

Part 1: The safety policy

  • Critical violations, which must be zero: moving money without authorisation, exposing another customer's data, hijacked instructions and harmful content
  • Tracked violations, which are measured and fixed: prompt leaks and rule-breaking replies

Part 2: Free checks on every baseline run

  • Unauthorised refunds, judged from the mock database's end state, not from the reply
  • Leaked emails and leaked system instructions, found by string search

Part 3: OpenAI Moderation

  • A baseline for generic harm, which never sees this store's business rules

Part 4: A judge for the store's own rules

  • A GEval rubric keyed to each case's policy tags, given both the reply and the actions taken

Part 5: Indirect prompt injection

  • A poisoned support article with a canary, to test whether retrieved text can take control
  • Counting only the runs that actually retrieved the poisoned chunk

  • Vulnerabilities (what to break) crossed with attack styles (how)

Module F: Judges and calibration

Notebook 10: Custom Judges

Status: Written, not yet run. Reads: data/golden_set.json, data/golden_runs.json, data/golden_runs_gpt-4o-mini.json (the same 121 cases on the first app model, shipped with the repository). Writes: data/custom_judge_scores.json. Keys: NEBIUS_API_KEY only, because nothing here runs the agent. Evaluations: §13 custom judges.

Part 1: Rubric judges with GEval

  • House rules no library ships a metric for: tone, policy wording and escalation phrasing
  • Writing evaluation_steps yourself and reviewing them like code. With criteria alone, the judge invents its own steps
  • strict_mode=True for a pass/fail verdict a person can also give, which makes calibration possible
  • Scoping each rule to the replies it applies to: "not applicable" is not a pass
  • A judge beside a free check, and what each one misses

Part 2: A decision-tree judge with DAGMetric

  • Walking the refund flow one small question per node, with a fixed score on each leaf
  • Facts about what the agent did come from code, and the judge checks the reply against them
  • The reply judge beside the end state: one judges what was said, the other what was done, and a release gate needs both

Part 3: A pairwise judge, with the positions swapped

  • Comparing two app versions answer by answer
  • A winner counts only if it wins in both positions, and flips measure position bias

Part 4: Save every verdict for calibration

  • Writes every verdict and its reason to data/custom_judge_scores.json, the input notebook 11 samples for human labels

Notebook 11: Calibrating Judges with Human Labels

Status: Planned. Writes: data/judge_trust.json. Evaluations: §14 judge calibration.

  • Sampling 50–100 verdicts per gating judge into a LangSmith annotation queue
  • A human labelling pass
  • Agreement in plain Python: Cohen's kappa, true-positive rate, true-negative rate and a confusion matrix
  • Bias checks: position, verbosity, and self-preference (the app model judging its own answers)
  • Revising any rubric with kappa below 0.6, then measuring again
  • A reference judge: gpt-4o beside the Qwen3 judge on the calibration cases, each scored against the human labels and the end-state checks, plus judge-vs-judge agreement
  • A judge trust table, one row per judge and metric, for the release gate
