01

What an eval actually is

2 TODOs

One example runs through this whole tutorial: a support bot for a phone company. Here is the run that explains why evaluation exists at all.

USER   "What's my balance on account ACC-99231?"
BOT    "Your Premium plan has a balance of $45.20."

That account does not exist. The lookup returned {"found": false} and the bot invented the rest — fluently, confidently, and about the customer's own money. Nothing crashed, nothing logged an error, and every test you had still passes.

A test asserts that the output equals something. You cannot do that here, because the same input gives different words every time. An eval asserts a property instead — is this grounded? did it refuse? did it call the right tool? — and returns pass or fail.

Normal software testEval
Same input twiceSame output, alwaysDifferent wording each time
What you assertAn exact valueA property: is it grounded? did it refuse?
ResultPass / failPass / fail, or a score you set a threshold on

That change of shape is the whole subject. Everything else is deciding which properties matter and how much it costs to check them.

In this repo

courses/01-rag-agent-tool-evaluation/00_Evaluation_Landscape.ipynb — the taxonomy, and section 4's decision procedure for picking a scorer.

1.1The metrics that measure words instead of truth

Before LLM judges, text was scored by word overlap with a reference: BLEU, ROUGE, BERTScore. You will meet all three in papers and interviews, and they fail in a specific, reproducible way.

Against "Refunds are available within 14 days of renewal", inserting the word not scores ROUGE-L 0.94 — while a correct paraphrase scores 0.09. The metric ranks the false answer ten times above the true one.

In this repo

courses/01-rag-agent-tool-evaluation/00_Evaluation_Landscape.ipynb §1c — both metrics implemented in ~30 lines of standard library so you can break them yourself.

02

Designing the process

5 TODOs

OpenAI's five steps, in the order you actually do them.

2.1Say what "good" means before you measure

"The bot should be helpful" cannot fail, so it is not a target. "Resolve 75% of billing questions without a human, and never state a balance for an account the lookup did not find" can.

Write the numbers first. Pick them after seeing a score and you will pick numbers the score passes.

In this repo

courses/02-databricks-mlflow-evals/00_eval_strategy_worksheet.ipynb — thresholds written before a single score existed.

2.2Collect cases from production, not from your desk

A test set you invented passes because it contains what you thought of. It is blind in exactly the way you are, and no amount of scoring fixes that.

Real sources: production logs, expert-written answers, historical tickets, and synthetic variants of all three. Tag every case so you can report by segment later.

In this repo

courses/03-agentic-eval-harness/03_the_golden_set.ipynb — 40 cases, stratified by language, intent and question type, with a datasheet and a content hash.

courses/02-databricks-mlflow-evals/04_eval_datasets_from_traces.ipynb — mining new cases out of production traces, and why hand-written sets are structurally blind.

2.3Metrics you can actually answer

"Is this good?" is not checkable. "Is every claim supported by the cited document?" is. Prefer questions with a yes or no.

The related rule is that models are better at choosing than at producing. Ask a judge to pick between two answers, or to classify one, rather than to write a score out of ten.

In this repo

courses/01-rag-agent-tool-evaluation/00_Evaluation_Landscape.ipynb — §4 is the code-first decision procedure and where a judge is genuinely required; §4f is the rule above stated properly, with the three shapes as a table and why each alternative drifts.

2.4Compare versions on the same inputs

One number alone tells you nothing. Run the old build and the new build over the same cases and diff them — and read the whole table, because the normal shape of a regression is one number up and one quietly down.

For the support bot, a version bump reads like this:

              v1      v2
groundedness  0.91    0.94   ▲ better
refusal       0.88    0.71   ▼ WORSE
resolution    0.76    0.79   ▲ better

v2 looks like a clear improvement until line 2. It got chattier, so it guesses where v1 would have said "I don't know" — and the guess is the ACC-99231 failure from §1, shipped.

In this repo

courses/02-databricks-mlflow-evals/05_prompt_versioning_and_regression.ipynb is built as exactly this trap: v2 improves the metric being watched and breaks three that are not.

2.5Keep measuring after launch

Offline you have a right answer to compare against. In production you never do, so the checks change shape: cheap deterministic rules on 100% of traffic, expensive judges on 1–2%.

In this repo

courses/03-agentic-eval-harness/12_online_evaluation_and_the_loop.ipynb — which metrics survive without a reference, five alerts, and two incident drills where you find out which alert stays silent.

03

Where the checks go

4 TODOs

What can go wrong depends on the shape of your system. Each shape adds exactly one new failure to the one before it.

3.1Tool choice and tool arguments are different bugs

"Asked about a bill, called reset_password" is a routing problem you fix in the prompt. "Called get_balance('99231') instead of get_balance('ACC-99231')" is a parsing problem. Same failed run, two different fixes, so two different checks.

In this repo

courses/03-agentic-eval-harness/05_tool_call_evaluation.ipynb — DeepEval's ToolCorrectnessMetric for the choice, ArgumentCorrectnessMetric for the arguments, and the result-handling section nobody writes.

3.2Did the task actually happen?

A fluent reply saying the refund was issued is not a refund. The only check that settles it reads the database, and no framework ships it because only you know what your tables should look like afterwards.

In this repo

courses/03-agentic-eval-harness/06_agent_handoff_and_end_to_end.ipynb Part 5 — the final-state check, including the "exactly once" property that catches a double refund.

3.3Routing, handoffs, and going round in circles

With several agents, two new things break: the router sends work to the wrong specialist, and the specialists pass a job back and forth without finishing it. The second produces no answer at all, expensively, and usually ends in a timeout rather than an error.

In this repo

courses/03-agentic-eval-harness/06_agent_handoff_and_end_to_end.ipynb — routing accuracy with a confusion matrix (Part 1), handoff payload integrity (Part 2), and loop detection (§2.1): a revisited agent, plus a hop bound for paths that never repeat.

3.4Report by segment, never as one number

An average hides the segment that is failing. The gate in this course blocks on the worst stratum, not the mean, and that choice is the reason the whole course exists.

In this repo

courses/03-agentic-eval-harness/10_stratified_reporting_and_statistics.ipynb — per-stratum reporting, and the arithmetic for how small a change a suite your size can actually detect.

04

Kinds of checker

6 TODOs

Three, and the rule for choosing is about reproducibility rather than money.

4.1If code can decide it, never pay a model

Code is free and gives the same answer every time — so when the number moves, the system moved. A judge's number moving tells you nothing on its own, because judges change their minds between runs.

In this repo

courses/03-agentic-eval-harness/07_safety_and_policy_checks.ipynb — four safety policies written as plain functions, and why there is no average anywhere in that notebook.

4.2Building a judge, three ways

GEval takes prose criteria. DAGMetric is an explicit decision tree. A RAGAS rubric fixes the level descriptions. Same job, different trade-offs between expressiveness and being able to answer "why this score?"

In this repo

courses/03-agentic-eval-harness/08_building_custom_judges.ipynb — all three on the same cases, and the table showing where they disagree.

4.3Your judge is biased in three specific ways

Position bias: it prefers whichever answer it saw first. Verbosity bias: it prefers the longer one. Same-model bias: it rates its own family's output highly. All three are testable, and all three are embarrassing to discover after shipping.

The analogy

Two wine judges. One always prefers whichever glass is handed over first; the other always prefers the fuller glass. Neither is tasting.

In this repo

courses/03-agentic-eval-harness/08_building_custom_judges.ipynb Parts 5, 5.1 and 6. Part 5 swaps the order and counts verdict flips; §5.1 audits the length distribution behind a win rate; Part 6 pits one model family against another.

4.4The length-controlled probe

The audit above shows quality and length are tangled. Separating them needs a controlled test: pad the worse answer until it is the longer one, then judge again. If the good answer still wins, length was not doing the work.

In this repo

The second cell of §5.1, behind a RUN_LENGTH_PROBE switch.

4.5Humans: the calibration source, not the throughput

You cannot have a person read every answer. You can have two people read fifty, and use that to find out whether your judge agrees with them — which is the only thing that licenses using the judge on everything else.

Agreement alone is not enough. If 90% of replies are good and your judge says "good" every time, agreement is 90% and Cohen's kappa is 0, which is the correct score for a judge that has learned nothing.

In this repo

courses/03-agentic-eval-harness/09_human_feedback_and_calibration.ipynb — a labelling panel, kappa derived by hand, and using labels to set a threshold instead of guessing one.

4.6Blinded preference testing, and the second rater

Asking "which of these two is better?" needs three rules: hide which arm is the new build, randomise which side it appears on, and use two raters. Drop any one and the result is not measuring what you think.

Two humans who disagree with each other is a rubric problem, not a judge problem, and no amount of judge tuning fixes it.

In this repo

courses/03-agentic-eval-harness/09_human_feedback_and_calibration.ipynb §2.2 — the panel, human-to-human kappa, and a blinding check that the winner landed on the left about half the time.

Edge cases

2 TODOs

5.1Collect kinds, not examples

Twenty jailbreak strings that are all the same kind of attack will all pass, and the green tick tells you nothing about the kind you missed. Organise by attack surface instead: one example each of multilingual, multi-intent, typo, polite tool failure, instruction override, formatting conflict.

In this repo

courses/02-databricks-mlflow-evals/10_capstone_edge_cases_and_crossref.ipynb — five attack classes by three variants, plus edge_cases.py, which tracks the guide's own eleven-item list in code with a verdict and a justification per row.

5.2The polite failure is the dangerous one

A tool that returns {"found": false} instead of raising does not crash anything. The model skates past it, and the answer that follows is specific, confident, and wrong about the customer's own account.

The ambiguous_tool_response case in the same notebook, covering both read tools' not-found paths.

06

Improving with evals

2 TODOs

6.1The loop

Production traces get sampled, the odd ones get labelled by a human, the labelled failures become new golden cases, and the gate gets harder. That circle is the point of the whole exercise — the suite gets better at noticing precisely where it failed to notice.

In this repo

courses/03-agentic-eval-harness/12_online_evaluation_and_the_loop.ipynb Part 6 closes the loop back into notebook 09 and then notebook 03.

6.2Optimise the prompt, and gate the optimiser

Automated prompt optimisation works — and it optimises against your judge, so an optimised prompt can pass the same gate a human-written one fails while being worse. Align the judge first, then let the optimiser run, then gate its output like any other change.

In this repo

courses/02-databricks-mlflow-evals/08_automated_improvement_gepa.ipynb (GEPA), gated by phase 5 and aligned by phase 7.

6.3Five mistakes, in one line each

  • Measuring what is easy instead of what matters. A score for word overlap is not a score for correctness — §1.1 has the numbers.
  • Testing on questions you made up. Your test set passes because you wrote it.
  • "We tried it, it seemed fine." That is a demo, not an eval.
  • Ignoring the humans. If your judge disagrees with your support team, the judge is wrong.
  • Running it once. Before the release and never again means you find out from customers.

What the guide covers that this repo deliberately skips

Four topics are in OpenAI's guide and deliberately not built here. The reasons are recorded per row in openai-eval-guide-coverage-gaps.md:

  • Industry benchmarks (MMLU, leaderboards) — this repo is about application-specific evaluation, and the guide itself treats benchmarks as the thing you move past.
  • Purchased datasets — a data source with nothing to teach beyond the sentence.
  • Multimodal evaluation — every system here is text-only. Audio and image inputs need a different agent, not a different technique.
  • Reinforcement fine-tuning — the improvement lever here is the prompt.
  • "Start with the most capable judge, then optimise down" — followed, then overridden on evidence. Every judge here is pinned small, and course 03's gpt-4.1-mini is deliberate: gpt-4o-mini fell into repetition loops, with the measurements at courses/03-agentic-eval-harness/README.md line 149. Re-opening it would mean re-running three courses' judges to confirm a result already measured.
One genuine gap remains open

OpenAI's own Evals API and Graders tool. The repo teaches the same ideas in DeepEval, RAGAS, MLflow and Phoenix; the vendor's own surface is the one framework not represented, and it belongs in a new lab under labs/ rather than a numbered course.
