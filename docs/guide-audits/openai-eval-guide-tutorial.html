1

What an eval actually is

Neither of these two exercises costs anything

A test asserts that the output equals something. You cannot do that with the support bot, because the same question gives different words every time. An eval asserts a property instead — is this grounded? did it refuse? did it call the right tool? — and returns pass or fail.

That change of shape is the whole subject. Everything after it is deciding which properties matter and how much it costs to check them.

1.1

The metrics that measure words instead of truth

Before LLM judges, text was scored by word overlap with a reference: BLEU, ROUGE, BERTScore. You will meet all three in papers and interviews, and they fail in a specific, reproducible way.

Against “Refunds are available within 14 days of renewal”, inserting the word not scores ROUGE-L 0.94 — while a correct paraphrase scores 0.09. The metric ranks the false answer ten times above the true one.

Designing the process

OpenAI's five steps, in the order you actually do them

2.1

Say what “good” means before you measure

“The bot should be helpful” cannot fail, so it is not a target. “Resolve 75% of billing questions without a human, and never state a balance for an account the lookup did not find” can.

Write the numbers first. Pick them after seeing a score and you will pick numbers the score passes.

2.2

Collect cases from production, not from your desk

A test set you invented passes because it contains what you thought of. It is blind in exactly the way you are, and no amount of scoring fixes that.

Real sources: production logs, expert-written answers, historical tickets, and synthetic variants of all three. Tag every case so you can report by segment later.

2.3

Metrics you can actually answer

“Is this good?” is not checkable. “Is every claim supported by the cited document?” is. Prefer questions with a yes or a no.

The related rule is that models are better at choosing than at producing. Ask a judge to pick between two answers, or to classify one, rather than to write a score out of ten.

2.4

Compare versions on the same inputs

One number alone tells you nothing. Run the old build and the new build over the same cases and diff them — and read the whole table, because the normal shape of a regression is one number up and one quietly down.

courses/02-databricks-mlflow-evals/05_prompt_versioning_and_regression.ipynb

Built as exactly this trap: v2 improves the metric being watched and breaks three that are not.

              v1      v2
groundedness  0.91    0.94   ▲ better
refusal       0.88    0.71   ▼ WORSE
resolution    0.76    0.79   ▲ better

v2 looks like a clear improvement until line two. It got chattier, so it guesses where v1 would have said “I don't know” — and that guess is the ACC-99231 answer at the top of this page, shipped.

Where the checks go

Each system shape adds exactly one new failure to the one before it

3.1

Tool choice and tool arguments are different bugs

“Asked about a bill, called reset_password” is a routing problem you fix in the prompt. “Called get_balance('99231') instead of get_balance('ACC-99231')” is a parsing problem. Same failed run, two different fixes, so two different checks.

Did the task actually happen?

A fluent reply saying the refund was issued is not a refund. The only check that settles it reads the database, and no framework ships it, because only you know what your tables should look like afterwards.

3.3

Routing, handoffs, and going round in circles

With several agents, two new things break: the router sends work to the wrong specialist, and the specialists pass a job back and forth without finishing it. The second produces no answer at all, expensively, and usually ends in a timeout rather than an error.

courses/03-agentic-eval-harness/06_agent_handoff_and_end_to_end.ipynb

Routing accuracy with a confusion matrix (part 1), handoff payload integrity (part 2), and loop detection (§2.1): a revisited agent, plus a hop bound for paths that never repeat.

Run §2.1 and the clean set flags zero loops — because none of the 25 recorded trajectories contains a handoff at all. A check that has never gone red is not evidence that it works.

Report by segment, never as one number

An average hides the segment that is failing. The gate in this course blocks on the worst stratum, not the mean, and that choice is the reason the whole course exists.

4.1

If code can decide it, never pay a model

Code is free and gives the same answer every time — so when the number moves, the system moved. A judge's number moving tells you nothing on its own, because judges change their minds between runs.

4.3

Your judge is biased in three specific ways

Position bias: it prefers whichever answer it saw first. Verbosity bias: it prefers the longer one. Same-model bias: it rates its own family's output highly. All three are testable, and all three are embarrassing to discover after shipping.

Picture two wine judges. One always prefers whichever glass is handed over first; the other always prefers the fuller glass. Neither is tasting.

The length-controlled probe

The audit above shows quality and length are tangled. Separating them needs a controlled test: pad the worse answer until it is the longer one, then judge again. If the good answer still wins, length was not doing the work.

4.5

Humans are the calibration source, not the throughput

You cannot have a person read every answer. You can have two people read fifty, and use that to find out whether your judge agrees with them — which is the only thing that licenses using the judge on everything else.

courses/03-agentic-eval-harness/09_human_feedback_and_calibration.ipynb

A labelling panel, kappa derived by hand, and using labels to set a threshold instead of guessing one.

Agreement alone is not enough. If 90% of replies are good and your judge says “good” every time, agreement is 90% and Cohen's kappa is 0 — the correct score for a judge that has learned nothing.

Exercise 16 of 21 no cost
4.6

Blinded preference testing, and the second rater

Asking “which of these two is better?” needs three rules: hide which arm is the new build, randomise which side it appears on, and use two raters. Drop any one and the result is not measuring what you think.

Two humans who disagree with each other is a rubric problem, not a judge problem, and no amount of judge tuning fixes it.

The panel, human-to-human kappa, and a blinding check that the winner landed on the left about half the time.

Edge cases

Organise by attack surface, not by example

5.1

Collect kinds, not examples

Twenty jailbreak strings that are all the same kind of attack will all pass, and the green tick tells you nothing about the kind you missed. Organise by attack surface instead: one example each of multilingual, multi-intent, typo, polite tool failure, instruction override, formatting conflict.

Improving with evals

Closing the loop, and gating the optimiser

6.1

The loop

Production traces get sampled, the odd ones get labelled by a human, the labelled failures become new golden cases, and the gate gets harder. That circle is the point of the whole exercise — the suite gets better at noticing precisely where it failed to notice.

Exercise 20 of 21 no cost
6.2

Optimise the prompt, and gate the optimiser

Automated prompt optimisation works — and it optimises against your judge, so an optimised prompt can pass the same gate a human-written one fails while being worse. Align the judge first, then let the optimiser run, then gate its output like any other change.

Exercise 21 of 21 no cost
6.3

Five mistakes, one line each

  • Measuring what is easy instead of what matters. A score for word overlap is not a score for correctness — §1.1 has the numbers.
  • Testing on questions you made up. Your test set passes because you wrote it.
  • “We tried it, it seemed fine.” That is a demo, not an eval.
  • Ignoring the humans. If your judge disagrees with your support team, the judge is wrong.
  • Running it once. Before the release and never again means you find out from customers.

What the guide covers and this repo skips

Five deliberate omissions and one open gap

  • Industry benchmarks (MMLU, leaderboards) — this repo is about application-specific evaluation, and the guide itself treats benchmarks as the thing you move past.
  • Purchased datasets — a data source with nothing to teach beyond the sentence.
  • Multimodal evaluation — every system here is text-only. Audio and image inputs need a different agent, not a different technique.
  • Reinforcement fine-tuning — the improvement lever here is the prompt.
  • “Start with the most capable judge, then optimise down” — followed, then overridden on evidence. Every judge here is pinned small, and course 03's gpt-4.1-mini is deliberate: gpt-4o-mini fell into repetition loops, with the measurements at courses/03-agentic-eval-harness/README.md line 149. Re-opening it would mean re-running three courses' judges to confirm a result already measured.
