Agent evaluation · applied

Evaluation harness in practice

The same mental model, instantiated on an enterprise RAG agent and on a multi-agent system that calls tools.

0 · The model in one paragraph

Instrument the agent so every run leaves a trace. Run it over a query set where labels are optional. Score along three independent axes — by layer, by requirement, by mechanism. Freeze a baseline. Gate: safety blocks absolutely, quality blocks statistically per stratum, cost is reported. Ship as a canary. Run the same reference-free scorers on sampled live traces. Collect human feedback, use it to calibrate the judges and grow the golden set. The loop's only real ground-truth source is production.

Requirementreference-free / reference-basedDo I need a labeled expected output?
Mechanismcode scorer / LLM judgeCan a function decide this, or only an opinion?

Everything below is these three axes applied to two system shapes.

0.5 · Two terms, precisely

Both words appear throughout the stages below and both are routinely used loosely. Worth pinning down.

"Instrument"

Adding tracing to your agent code so every run emits a structured record of what happened internally — not just the final answer. The term comes from observability: instrumenting code means wrapping operations so they emit spans.

  • One span = one operation, with start time, end time, inputs, outputs, and a parent.
  • Spans nest, so a single run becomes a tree: the run at the root, retrieval and tool calls as children.

A trace is a nested tree of spans, not a flat log line.

In practice it's two lines of work

  • Autolog — MLflow and similar tools auto-instrument LangGraph, LangChain and the model SDKs. One call gives you spans for model calls, tool calls and graph node transitions for free.
  • Manual spans and attributes for what the framework can't know: the rewritten query, chunk document IDs and versions, the approval decision and its timestamp, the row written to the database, prompt and model version tags.

Why the harness depends on it

  • Groundedness needs the retrieved context stored beside the answer. No span, no metric.
  • Trajectory scoring needs the ordered list of tool calls with their arguments.
  • Blame attribution needs parent-child structure to find the first step that failed.
  • Online evaluation needs live traces to sample from — production has no eval dataset, only traces.
  • Replay of regression cases comes from stored traces.
Instrumenting makes the agent's internals observable as data. Evaluation doesn't create that data — it only scores it. Skip instrumentation and you can score the final answer and nothing else.

"Canary"

A deployment pattern: release the new version to a small slice of real traffic first, watch it, and roll back automatically if guardrail metrics move the wrong way. Named after the canary in a coal mine — a small thing that fails first so the rest doesn't.

The 95% on the old version is a live control group, not just untouched traffic.

Why it belongs in the harness

  • Statistical power. A 200-case offline suite can't detect a 3-point regression. A canary sees thousands of real requests in a day.
  • Real distribution. Your golden set is what you imagined users ask; the canary is what they actually ask, long tail included.
  • Contained blast radius. If the new version is worse, 5% of users saw it for an hour, not 100% for a week.
  • Built-in control group. Concurrent comparison, so traffic-mix drift doesn't contaminate the result the way a month-old baseline would.

What you watch during one

  • Safety assertions (code scorers, 100% of canary traffic) — any firing is an instant rollback, no discussion.
  • Reference-free judge scores on sampled traces — groundedness, reply quality.
  • Operational: p95 latency, error rate, cost per request, steps per resolution.
  • Implicit user signals: re-ask rate, escalation rate, thumbs-down rate.

Typical shape

  • Start at 1–5%, hold long enough to accumulate volume, then ramp 25% → 50% → 100%.
  • Rollback is pre-wired and automatic, not a human noticing a dashboard at 3am.
  • Stratify the canary cohort, or you'll accidentally route it one tenant's traffic and measure nothing.
The release gate is the last offline check; the canary is the first online one. The gate blocks a merge on a small sample; the canary blocks a full rollout on a real one.

A · Enterprise RAG agent

System. A policy question-answering agent over an internal BFSI document corpus. Single agent: retrieve → ground → answer with citations. Serves eleven business units with different document sets.

The one-line risk: it answers confidently from the wrong document, or from nothing at all, and nobody notices because the aggregate accuracy looks fine.

Scorers tap the pipeline at every stage, not just the final answer.

A1 · Instrument

  • the rewritten query actually sent to the retriever
  • every retrieved chunk with document ID, version, score
  • the answer with the citation IDs it claims
  • model, prompt and embedding-model versions

Why: groundedness is meaningless without the retrieved context stored beside the answer; citation validity is unverifiable without chunk IDs.

A2 · Query set

SourceWhat it gives you
SME / PRD questionsThe 30 questions the business says must work
Generated from the corpusTake a chunk, have a model write the question it answers — free, immediate groundedness cases
Absent / unanswerableQuestions the corpus genuinely cannot answer. The most important category.
AdversarialAmbiguity, internal abbreviations, multi-hop, out-of-scope
Replayed prod trafficVolume and real distribution — only once you have it

Strata: business unit, language, question type. Labels get added to the hard cases over time — you do not wait for them.

A suite with no "absent" cases trains you to ship an overconfident system.

A4 · Baseline and gate

Blocks absolutely — code

  • any response containing PII
  • any citation ID not present in the retrieved set
  • any response asserting a commitment ("we will approve your loan")

Blocks statistically — judges, paired vs. baseline

  • groundedness, relevance, correctness
  • per business unit, with a minimum case count per stratum

Reported

  • tokens, latency, cost per query
🔍 Deep dive — the failure this design exists to prevent

A retrieval change lifts aggregate accuracy 79% → 81% and ships. Two weeks later one business unit escalates: their segment fell 82% → 67%. They were 4% of the eval set, their corpus is abbreviation-heavy, and the change shifted weight from lexical to dense retrieval — exactly the direction that hurts exact-token matching on abbreviations. The aggregate improvement was real; the segment collapse was invisible inside it.

Fix: a per-stratum floor. No release may drop any stratum by more than three points regardless of the aggregate. Every business unit is its own stratum with a minimum case count, so a small tenant is never statistically invisible.

A5 · Online

  • Groundedness, relevance and refusal-appropriateness on sampled live traces (judges cost money).
  • Code scorers on 100% — citation validity, PII, schema. They're free.
  • Per-tenant rolling accuracy proxy with automatic alerting, so the next segment collapse is caught in days, not weeks.

A6 · Human feedback

  • End-user: thumbs, "this didn't answer my question", re-ask rate within a session.
  • Expert: SMEs annotate a weekly sample — was the answer correct, was the citation the right one.
  • Feed back: calibrate the groundedness and correctness judges with Cohen's kappa; promote every escalation into a permanent golden case.
🎯 Interview pointer Don't open with faithfulness. Open with: "I separate retrieval failures from generation failures, because the fix is different — one is an indexing problem, the other is a prompting problem. Then I gate on groundedness per tenant, because aggregate quality hides exactly the segment collapses that generate escalations."

B · Multi-agent system calling tools

System. Customer support. Supervisor routes an issue → Knowledge agent (cited policy retrieval) → Billing agent (invoice lookup, refund request) → human approval gate → reply.

The one-line risk: every individual component passes its own check, and the system still issues a refund to the wrong customer.

Every level is scored separately, so a failure can be attributed to a component.

B1 · Instrument

  • the supervisor's routing decision and its confidence
  • every tool call: name, arguments, return value, latency, error
  • every handoff: exactly what context crossed between agents
  • every approval request, its outcome, and its decision time
  • the final state write — refund row, ticket update

Why: in a multi-agent system the trajectory is the product. An output-only evaluation tells you nothing about which of five components failed.

B2 · Query set

Cases are scenarios, not question/answer pairs. Each carries the customer message, the seeded system state, the expected route, the expected trajectory, the expected final state, and strata (intent, language, handoff vs. single-agent).

Add fault-injection switches to prove the scorers actually catch things:

The final-state check is the metric no framework gives you and the one that matters most. The agent saying "I've processed your refund" is a string. The refund row existing, once, for ₹2,400, against the right customer, is the truth. Only a code scorer can see it.

🔍 Deep dive — blame attribution

Use span-level scores to find the first level that failed, and count failures per agent. Without this, every end-to-end failure reads as "the system was wrong" and nobody knows what to fix. A routing error and a bad tool argument produce the same failed task, but one is a supervisor prompt problem and the other is a tool-schema problem.

Practical form: for each failed case, walk the trace forward and record the earliest scorer that flipped to fail. Aggregate that into a failure-count-per-component table. That table is your engineering backlog.

B4 · Baseline and gate

Blocks absolutely — code, per case, never averaged

  • refund issued without a recorded approval
  • any agent touching another agent's tools
  • cross-customer data access
  • duplicate state writes — the same refund twice
  • PII in the customer-facing reply

Blocks statistically — paired vs. baseline, per stratum

  • routing accuracy, task completion, reply quality
  • strata: intent, language, single-agent vs. handoff

Reported

  • steps per resolution, tool calls per resolution, cost, p95 latency
Watch thisA flaky safety test is a safety problem, not an annoyance. If skip_approval blocks only 97% of the time, you do not have an approval control.

B5 · Online

  • Code scorers on 100% of live traffic: approval-before-refund, role adherence, duplicate writes, handoff integrity. All reference-free, all cheap.
  • Judges on a sample: reply quality, topic adherence.
  • Operational guardrails: routing-confidence drift, retry-rate spike, steps-per-resolution creep (a silent cost regression), tool error rates.
  • Automatic rollback the moment a safety assertion fires in production.

B6 · Human feedback

  1. Runtime approvals — and evaluate the gate itself: decision time, queue depth, and the rubber-stamp signal (approval rate near 100% with near-zero decision time means the control has degraded into a click).
  2. End-user: resolution confirmed, ticket reopened, escalation to a human.
  3. Expert annotation: replay a sampled trajectory and mark the first step that went wrong. This labels the trajectory, which is what you need to improve routing and handoffs.

Feed back: calibrate the reply-quality judge; turn every production incident into a scenario case with its own fault switch.

🎯 Interview pointer The weak answer to "how do you evaluate a multi-agent system" is "task completion rate". The strong one: "Per level, with blame attribution — a single end-to-end score tells me the system failed but not which of five components to fix. And the hard gate is state assertions, not judge scores: the agent claiming it issued the refund and the refund existing are different facts."

The shape of the difference: RAG evaluation is mostly about what was said, so judges carry more weight and calibration matters enormously. Multi-agent evaluation is mostly about what was done, so deterministic code scorers carry more weight and the gate is far more assertable.

Mistakes that get caught in interviews

  • Averaging safety. A 99.2% approval-compliance rate is a failed gate, not a good score.
  • Absolute thresholds on judge scores. "Faithfulness > 0.85" bakes the judge's current calibration into CI. Gate on movement vs. baseline.
  • Aggregate-only floors. Compatible with a large collapse in the segment that generates your escalations.
  • Evaluating the output when the failure is in the trajectory. Especially fatal in multi-agent.
  • Reporting judge scores with no agreement figure. A judge is an unvalidated classifier until you measure kappa against humans.
  • Claiming determinism you didn't earn. Unfrozen fixtures, unpinned versions, unseeded shuffles — then wondering why the gate is flaky.
  • Underpowered comparisons. A 200-case suite cannot detect a 5-point change; measure small ones in a canary.
  • No fault injection. If you have never deliberately broken the system and watched the suite go red, you do not know the suite works.
