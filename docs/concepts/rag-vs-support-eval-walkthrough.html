Offline eval, online eval, release gate — on two real systems

Same three-layer framework, applied to an Enterprise RAG assistant and a multi-agent customer support system. No architecture deep dive — just what gets measured, when, and what blocks a release.

If production has no reference answers, what is the "online judge" actually scoring?

Not the same thing offline scoring does. Production doesn't run a golden-answer comparison — it runs three different techniques, none of which need a labeled correct answer. Click each.

🔗Self-consistency judgingmost of what "online judge" means

The judge doesn't compare the answer to a golden reference — it compares the answer to its own retrieved context, which production already logs as part of the trajectory. "Is every claim in this answer entailed by the passages this exact run retrieved?" needs zero external ground truth, because the reference — the context — travels with the run itself.

RAG example: faithfulness/groundedness, citation accuracy, contradiction-disclosure — all scored against the run's own context.

Support example: "did the reply match what the tool actually returned" — scored against the tool's logged output, not a human-written answer key.

⚖️Deterministic trajectory rulesno judge model needed

Safety and policy checks were never comparisons to a reference answer in the first place — offline or online. "Did it call the write-tool without an approval step," "did it cross a tenant boundary" are pass/fail assertions read directly off the logged trajectory. These run online exactly as they run in the gate, at full volume, for free.

🎯Periodic human labels — for calibration, not live scoringcloses the loop

A small sample of production runs is sent to human reviewers, but on a delay, in a batch — not inline per-request. That labeled batch does two jobs: it measures how well the LLM judge agrees with a human on the same cases (a kappa score, watched for drift), and it becomes new golden-set cases, feeding the offline suite so it stops describing last quarter's traffic. The judge scores every live sample instantly and self-referentially; the human sample calibrates whether those scores can still be trusted.

⚖️Paired canary comparisonrelative, not absolute

For an actual A/B or canary rollout, the question isn't "is this answer correct" in isolation — it's "does variant B win, lose, or tie against variant A on the same live question." A judge (or a real user signal) picks a winner per pair. That's a relative verdict, which needs no ground truth either — only two things to compare.

In short: production substitutes the logged context for a golden answer wherever it can (most of the time), falls back to rule-based assertions where no judgment call is needed at all, and only reaches for actual human-labeled ground truth in small, delayed samples — used to keep the judge honest and the offline suite fresh, not to score every request.

So do offline and online share metrics? Yes — but split three ways, not identical sets.
Offline-only need a labeled reference — can't run without one
  • Answer correctness vs. a written reference answer
  • Task resolution accuracy vs. the known-correct action
  • Anything scored by comparing to a human-authored "right answer"
Runs in both reference-free or rule-based — same computation either place
  • Faithfulness / groundedness (context is its own reference)
  • Citation accuracy, contradiction disclosure
  • Safety & trajectory assertions (approval, tenant isolation)
  • Router-confidence disagreement style checks
Online-only the phenomenon only exists once real traffic exists
  • Deflection / CSAT, escalation rate, reformulation rate
  • p95 latency, cost-per-success drift, queue depth
  • Tool status mix, cache hit rate, corpus/traffic drift

The system, in one line: answers employee/customer questions by retrieving from internal + licensed document corpora and synthesizing a cited response — the thing being evaluated is "is this answer grounded, correct, and safe to hand to a regulated business," not the retrieval pipeline's internals.

01 Offline evaluation pre-launch, frozen suite

Runs on a versioned golden set of questions with known correct answers and known supporting source documents — deterministic, repeatable, computed before any real user sees the build. Click a metric to see what it's built to catch.

Context recall @ k
≥ 92%▾
Did the retriever pull the chunk that actually contains the answer, within the top-k results? If this is low, nothing downstream can be right — the model never saw the fact.
Context precision / MRR
MRR ≥ 0.8▾
Of what's retrieved, how much is relevant, and how high-ranked is the correct passage? Low precision buries the right chunk under noise, which quietly increases hallucination risk even when recall looks fine.
Faithfulness / groundedness
≥ 90%▾
Is every claim in the answer actually supported by the retrieved context (checked via NLI/judge entailment)? This is the number the research-assistant case study moved from 78%→91% by adding a grading step before synthesis.
Answer correctness vs. reference
paired, vs. baseline▾
Does the answer match a human-written reference answer for the same question, judged per-case and paired against the previous build — not scored in isolation, so noise from question difficulty cancels out.
Citation accuracy
≥ 97%▾
Do the cited sources actually contain the claim they're attached to? This is what caught "citation drift after compaction" in the research-assistant case study — summarization silently dropped source identifiers.
Refusal correctness (absent stratum)
≥ 95%▾
On questions the corpus genuinely can't answer, does the system refuse instead of confabulating? Without this stratum, every "improvement" that just answers more confidently looks like progress.
Contradiction handling
correct disclosure▾
When two sources disagree, does the system surface the disagreement instead of silently picking one? Silent resolution is a correctness bug even when the picked answer happens to be right.
PII / compliance leakage rate
0 tolerated▾
Trajectory-level assertion, not a quality score: did any response expose another customer's data, or give advice outside the DPDP/RBI-permitted scope? This is a safety check, scored pass/fail per case, not averaged.

02 Online evaluation live traffic, continuous

Runs against real production conversations after launch — this is where small regressions and corpus drift actually get caught, because the sample size the offline suite lacks exists here.

Sampled online judge score
1–2% of traffic▾
A random slice of live runs is continuously re-scored by the same harness used offline. Availability monitoring only answers "did it respond" — this is the only signal that answers "was it right," and those are different questions.
Citation-free answer rate
alert on rise▾
The tell for a silently-empty index: an index rebuild that returns zero rows still returns HTTP success, so error-rate monitoring stays green while quality collapses. This metric is what actually catches it.
User reformulation rate
trend, per segment▾
How often a user immediately re-asks the same question differently — a cheap proxy for "the first answer didn't help," available without any explicit feedback button.
Escalation-to-human rate
trend, per department▾
Rising escalation on a specific document class (retail vs. corporate vs. compliance corpora) localizes a regression to a stratum long before the aggregate metric moves.
Cost per successful query
alert at 3× median▾
Not total spend, which just tracks traffic. A prompt change that quietly doubles retrieved-context size shows up here first — before finance notices the bill.
Redaction / guardrail trigger rate
trend + spike alert▾
A sudden spike usually means a new query pattern is probing a boundary the offline suite never sampled — the live signal that a compliance gap exists before an incident does.

03 Release gate CI, blocks promotion

Turns the offline metrics above into one automated decision on every candidate build, stratified by document class / business unit rather than only the aggregate.

  • Safety — blocks absolutely: any PII/tenant-isolation leak, or any answer giving out-of-scope regulated advice, on any case in the suite.
  • Aggregate floor: faithfulness ≥ 90% and answer correctness not regressed beyond tolerance, tested paired against the baseline build.
  • Per-stratum floor: no document class / business unit (retail, corporate, compliance, regional) may drop more than 3 points — this is what a retrieval-weighting change can silently break for one corpus while improving the mean.
  • Cost ceiling: cost per successful query stays under budget — a context-window change that improves faithfulness by resending more of the corpus is a visible trade-off, not a silent one.

The system, in one line: routes 60,000 conversations/day across 9 languages to 11 deterministic workflows (≈84% of volume) or a bounded agent loop for the residual tail — what's being evaluated is "did it resolve the right way, safely, within cost and latency budget," not the router's internals.

03 Release gate CI, blocks promotion

Same four-check shape, tuned to this system's actual SLA and safety surface.

  • Safety — blocks absolutely: any refund or plan-change action executed without passing the approval queue; any regional data-residency violation.
  • Aggregate floor: deflection ≥ 45% at the satisfaction floor, tested paired against baseline — with enough cases to actually detect the delta, not noise.
  • Per-stratum floor: no language may drop more than a set margin regardless of aggregate deflection — the exact check that caught the 15-point gap before it shipped.
  • Cost ceiling: ≤ $0.06 per conversation, plus the router confidence floor itself is gated on shadow-run disagreement staying under ~3% before any change to it promotes.

The pattern repeats across both systems on purpose: offline catches large, deterministic, safety-critical regressions cheaply and fast; online catches small drift and anything the offline dataset never represented, because that's where the traffic — and the statistical power — actually is; the gate is what makes the offline layer actually stop a bad build, instead of being a number someone might glance at.
